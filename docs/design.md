# design — v0

WHY는 `docs/WHY.md` 참조.

## v0 범위

장면 촬영 한 장으로 물건 목록을 만들고, 이름을 붙이고, 검색할 수 있다.
개별 촬영으로 표본 이미지를 채운다. 도감 화면에서 진행 상태를 본다.

범위 밖: 재촬영 diff, 침전층 리포트, 색 팔레트, 총액, 공유 페이지, 소셜.
그리드 출력은 크기순 기본형만.

## 데이터 모델

### 노드

물건과 군집은 같은 테이블. `kind`로 구분한다. 군집을 별도 테이블로 빼면
lazy split 때 마이그레이션이 생긴다.

```
Node
  id
  dex_no          최초 발견순 정수. 절대 재정렬하지 않는다
  kind            'object' | 'cluster'
  parent_id       군집 소속 (nullable)
  label           사용자 확정 이름
  label_ai        AI 추정 이름 (보존. 사용자가 고쳐도 지우지 않는다)
  category
  zone            'hot' | 'warm' | 'cold'
  splittable      false면 개별 분리 시도 안 함
  member_count    군집일 때 추정 개수
  status          'active' | 'gone'
  label_status    'pending' | 'confirmed' | 'deferred'. 아래 참조
  missed_count    연속 미검출 횟수. 퇴장 확인 큐의 근거
  discovered_at   최초 발견 (dex_no 근거)
  departed_at     퇴장. status='gone'일 때만
  image           아래 참조
  note            자유 메모 (마크다운)
  needs_input     AI가 식별 실패. 명명 큐 우선순위
```

`label_ai`를 남기는 이유: AI가 내 물건을 뭐라고 불렀는지가 그 자체로 콘텐츠고,
나중에 모델 교체 시 정확도 비교 근거가 된다.

**`label_status`가 필요한 이유**: `label`이 비어있다는 사실만으로는 "아직 명명
스와이프에서 안 봤다"와 "봤는데 애매해서 나중에로 넘겼다"를 구분할 수 없다.
이 둘은 큐에서 다르게 취급해야 한다 — 미확인 항목이 우선이고, 미룬 항목은
뒤로 밀리되 없어지지 않는다. 그리고 WHY의 v0 성공 판정 1번(명명 완주율 =
"장면 촬영 후 생성된 노드 중 이름이 붙은 비율")의 분자·분모가 바로 이 필드로
정의된다 — `confirmed` 개수 나누기 `active` 노드 총수.

- `pending` — 생성 직후 기본값. 명명 스와이프 큐 앞쪽
- `confirmed` — 사용자가 오른쪽으로 넘겼거나(AI 추정 그대로) 수정 후 확정.
  `label`이 채워진다
- `deferred` — "나중에". `label`은 계속 비어 있고, 큐 뒤쪽으로 밀린다

**퇴장은 파이프라인이 판정하지 않는다.** 같은 책상을 같은 시각에 두 각도로 찍은
사진에서 물건 집합이 달랐다 — 한 장면의 미검출은 부재의 증거가 아니다. 미검출은
`missed_count`만 올리고, 3회 연속이면 확인 큐에 올린다. `status='gone'`은 사용자가
누를 때만 붙는다. 근거는 `docs/scene-schema.md` §12.

### 이미지 참조

파일로 저장하지 않는다. 장면 + bbox 참조로 두면 bbox 수정 시 재크롭이 공짜고,
세그멘테이션 모델이 좋아졌을 때 과거 장면을 소급 재처리할 수 있다.

```
image:
  { type: 'none' }
  { type: 'derived',  scene_id, bbox: [x0,y0,x1,y1] }   정규화 0~1, 좌상단 원점
  { type: 'specimen', file_id }                          누끼 PNG
```

`crop_quality`가 임계값 미만이면 `derived`로 승격하지 않고 `none`으로 둔다.
알아볼 수 없는 얼룩을 보여주느니 실루엣이 낫다.

### 활동 / 엣지

v0에서는 활동 노드를 만들지 않는다. 군집에 `activity` 문자열 필드만 둔다.
정리 제안(불일치 거리 계산)이 들어올 때 정식 노드로 승격한다.

### Scene

```
Scene
  id
  captured_at
  place           장소 태그. 'office' | 'cafe:합정' 같은 자유 문자열
  image_file_id
  surface_bbox        책상 상판 영역
  capture_quality     angle, surface_ratio, position_confidence
  screen_masks        모니터 화면 영역. 파싱 제외 + 공유 시 블러
```

`screen_masks`는 v0 필수다. 화면에 뜬 내용을 물건으로 오인하는 문제와
사생활 문제를 동시에 처리한다.

### 도감의 범위

**노드는 사용자 단위로 하나의 도감이다.** `dex_no`는 장소와 무관하게 하나의
연속된 수열이고, 장소는 `Scene`에만 붙는다.

지갑, 에어팟, 책, 노트북은 실제로 사무실과 카페를 오간다. 장소별로 도감을
나누면 같은 물건이 양쪽에 중복 등록되고 `dex_no`를 두 번 소모한다. WHY도
"내 물건을 기록하는 도구"라고 했지 "내 책상"이라고 하지 않았다.

매칭은 **같은 `place`의 노드를 먼저 보고, 못 찾으면 전체로 넓힌다.** 장소가
다르면 위치 신호를 아예 쓰지 않는다. 진행률의 분모는 장소로 필터링해서
"이 책상의 n/N"을 보여줄 수 있다.

### 내보내기

노드 하나 = `.md` 파일 하나. 프론트매터에 속성, 본문에 note. 이미지는
`assets/` 동봉. 전체 zip.

## 촬영 2종

| | 장면 (Scene) | 개별 (Specimen) |
|---|---|---|
| 목적 | 발견 — 존재와 배치 기록 | 포획 — 표본 이미지 확보 |
| 대상 | 책상 전체 1장 | 물건 하나 |
| 누끼 품질 | 불필요 | 필수 |
| 처리 | VLM 파싱 → 노드 일괄 생성 | 배경 제거 → 이미지 교체 |
| 빈도 | 주 1회 | 내킬 때 하나씩 |

개별 촬영은 물건에 서사를 붙일 자연스러운 순간이다. 이때 note 입력을 띄운다.
장면 사진에서는 안 보이던 것(스티커, 각인, 흠집)이 여기서 주인공이 된다.

## 파이프라인

### 장면 파싱

```
사진 업로드
  → screen_masks 검출 (화면 영역 마스킹)
  → VLM 1회 호출: 물건 + 군집 + bbox + 침전 후보를 JSON으로
  → 기존 노드와 매칭 (label + bbox 근접도)
  → 신규 노드에 dex_no 부여
  → crop_quality 판정 → image.type 결정
```

VLM 호출은 1회로 끝낸다. 세그멘테이션 모델을 별도로 돌리지 않는다. v0에서는
bbox 크롭으로 충분하고, 정밀 마스크가 필요한 건 개별 촬영 쪽이다.

출력 스키마, 임계값, 프롬프트, 후처리 순서는 `docs/scene-schema.md`.
실측 검증은 아직. 사진 4장이 필요하다.

### 개별 촬영 누끼

  머리카락 수준 알파 매팅. 단일 피사체에는 최상급
- 그 외: 배경 제거 API 폴백
- **iOS 네이티브 우선으로 결정.** 누끼 품질이 카드 톤을 좌우하고, 온디바이스

  둘 수 없다). 웹은 나중

**착수 전 손검증 필요**: 단축어 앱 "배경 제거"로 티팟·머그·키보드 등 10개를
직접 만들어서 카드 톤이 실제로 예쁜지 확인. 반나절.

## 화면

### 1. 도감 (홈)

기본 화면. 목록이 코어이므로 그리드가 아니라 도감이 홈이다.

- 카드 3상태: 미기록(실루엣) / 파생(사각 크롭, 저채도) / 표본(누끼, 컬러)
- 진행률 `n/N 표본 확보`
- 정렬 토글: 도감번호순(기본) / 군집순
- 퇴장 항목은 별도 탭. 회색 처리 + 퇴장 라벨

실루엣은 카테고리 아이콘이 아니라 bbox 형태를 채운 단색 실루엣으로 간다.
"아직 안 잡은 것"으로 읽혀야 한다.

### 2. 명명 스와이프

**실사용 시간의 대부분이 여기 쓰인다. UX 승부처.**

- 조각 하나를 크게. AI 추정 이름 미리 채움
- 맞으면 오른쪽 / 틀리면 수정 / 애매하면 나중에
- 목표 **한 조각당 2초**. 20개를 1분 안에
- 필수 필드는 이름과 카테고리뿐. 가격·구매일은 선택
- `needs_input` 항목을 앞에 배치
- 폼 채우기로 만들지 않는다

### 3. 검색

사람이 자발적으로 앱을 여는 유일한 이유는 "그거 어디 뒀더라"다.
검색 실패가 등록 유도 지점이다.

- 결과 없음 → 유령 노드 생성 제안. "찾으면 어디 있었는지 알려주세요"
- 유령 노드는 이미지 없이 이름만 있는 노드. 다음 장면 촬영에서 매칭 시도

### 4. 그리드 내보내기

도감에서 "내보내기". 크기순 정렬 격자. `crop_quality` 미달 항목은 제외.
v0는 PNG 저장만. 공유 페이지 없음.

## 정렬 이원화

같은 데이터, 두 배열.

- **공유용**: 크기순. 놀링의 미감은 크기순 정렬에서 나온다
- **기록용**: 군집순. 활동 단위 정보를 보존한다

## 진행률 분모

물건이 계속 늘어나면 분모가 커져 영원히 100%가 안 된다. 이건 의도된 것이다
(세대가 늘어나는 도감). 다만 완주 가능한 단기 목표가 별도로 필요하다.
v0에서는 "이번 주 촬영 대상 N개" 형태로 하위 목표를 둔다.

## 열린 질문

구현하며 결정한다.

- 군집 lazy split의 트리거. 사용자가 명시적으로 누르나, 개별 촬영이 들어오면
  자동으로 쪼개지나
- 체류 기간 등급의 구간. 며칠부터 올라가나
- 유령 노드와 실제 노드의 매칭 신뢰도 임계값

## 착수 순서

1. 단축어 누끼 손검증 (반나절) — 카드 톤 확인. 미착수
2. 장면 파싱 프롬프트 + 스키마 고정 — 실제 사진 3~4장으로. 스키마·검증
   도구(`docs/scene-schema.md`, `tools/`)는 되어 있고, 실측만 남았다
3. **데이터 모델 + 명명 스와이프 — 코드 작성 완료 (`ios/`), 컴파일 미검증**.
   1·2번과 독립적으로 먼저 했다 — 노드가 이미 있다고 가정하고 저장·명명만
   다룬다. 검증 상태와 남은 갭은 `ios/README.md`
4. 도감 화면
5. 검색
6. 그리드 내보내기
